# 0029: M4's plan: measured round 1 as a pilot, a USD 300 budget, Storybook as the docs site, one pull request per component

- Status: accepted
- Date: 2026-11-28
- Tracker: T-0060, F-0042, T-0061

## Context and problem statement

M4 builds the remaining 13 components, the docs site with the metrics table, and the second calibration ([ADR 0020](0020-component-list-and-npm-names.md)). Breaking T-0060 down raised four questions:

- **Measured runs:** the protocol puts measured round 1 (Button, Badge, Link and Dialog, five repeats each) at the end of M2, but it never ran: M2 generated each component once, and `fazon measure` isn't implemented (F-0042). Round 2 covers all 17 at the end of M4.
- **Budget:** [ADR 0021](0021-settled-questions.md) set USD 150 for measured runs and calibration rounds through M3 and left M4's budget to be set before its round. Expected: measured round 1 about $20–60, measured round 2 about $100–300, calibration round 2 with Sonnet 5.5 about $60 (Q-0030).
- **Docs site:** the brief deploys the Storybook site to GitHub Pages and puts the metrics table on "the site"; [workflow.md](../spec/workflow.md#from-m4-pages) leaves the site to T-0061.
- **Pull requests:** M2 used three or four pull requests per component in the example repository (the spec, the API, the fixtures and states, the generated code), which would be about 45 for 13 components.

## Considered options

1. Measured runs: run round 1 as `fazon measure`'s pilot, then round 2; or drop round 1 and run round 2 only.
2. Budget: USD 300, 400 or 500 for M4.
3. Docs site: Storybook is the site, with generated docs pages; a separate static site that links to Storybook; decide later.
4. Pull requests: one per component; two (the spec, then the generated code); as in M2.

## Decision outcome

The maintainer chose:

1. **Measured round 1 runs in M4, as `fazon measure`'s pilot,** on the four components that exist, before round 2 on all 17. A cheap first round finds the command's problems, as calibration round 1 found F-0041.
2. **USD 300 for M4's rounds:** measured rounds 1 and 2 and calibration round 2 share it. As before, a round compares its estimate with what's left before it starts, and waits for the maintainer's approval when it doesn't fit.
3. **Storybook is the docs site:** one build and one deploy, with generated docs pages: one per component from its spec, and a metrics page from the rounds' records.
4. **One pull request per component** in the example repository: its spec, approved API, fixtures, states and generated code together, opened after the maintainer's local review. The API is still approved with `fazon approve` before any code is written, and its hash is in the component's provenance, so the three decision points stay.

### Consequences

- measurement.md moves round 1 to M4 and records the USD 300 budget.
- T-0060 is broken into steps in the tracker: the framework's gaps first, `fazon measure` and its pilot, the components in three batches, calibration round 2, measured round 2, and the docs site.
- T-0061 specifies the docs site and `pages.yml` from this decision.
- A pull request per component is larger to review; the spec's API is the part to read first.
